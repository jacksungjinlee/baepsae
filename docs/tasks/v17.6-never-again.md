## Why v17.5 isn't enough on its own

v17.5 makes the daily job refuse to publish bad data. Users could still get wrong or stale data if:

1. **The job doesn't run at all** — GitHub outage, cancelled or disabled schedule, or the 60-day inactivity
   auto-disable. A gate inside the job can't report that the job never started.
2. **A code change breaks the app or the pipeline.** Jack can't read code, so tests must run on every change and block
   the merge.
3. **The live site differs from the repo** — a failed or old Pages deploy, or browsers holding old files.
4. **The monitor itself dies quietly**, along with everything else.

Ship as separate PRs in this order: **1 → 2 → 3a → 3b → 3c**.

## Part 1 — Watchdog: an independent check of the live site

`.github/workflows/watchdog.yml`

Workflow files can only be dispatched manually once they exist on `main`. Plan a stub merge if you need to test the
dispatch before the real logic lands.

**Triggers**
- schedule `30 7 * * 1-5` (16:30 KST, weekdays — after the daily run normally finishes);
- `workflow_run` on 시세 데이터 갱신 completed (after Part 3: on Deploy completed), plus a 10-minute wait for the Pages
  cache (`max-age=600`);
- manual.

**Checks**
- **Live files.** Download the four JSON files from `https://jacksungjinlee.github.io/baepsae/?t=<epoch>` paths and run
  `validate_data.py --live`.
- **Staleness vs two independent sources.** Expected `pxDate` = the later of:
  - the latest **final** `fdr_krx_data_cache` listing date before today (KST);
  - the last daily bar date of yfinance `^KS11` before today (KST).

  Alert if live `pxDate` < expected — but only when the check runs after 15:30 KST, so a run still in progress isn't
  flagged.
- **Run results.** The latest **completed** 시세 데이터 갱신 run on `main` (excluding `dry_run` runs) must have
  succeeded. In-progress runs don't count.
- **Page build.** `baepsae.html` returns 200, and its `<meta name="baepsae-build" content="{sha}">` (added to `build.sh`
  here) matches the commit that should be live. This catches Pages serving an old build.

**Alert**
- Keep exactly one open issue `뱁새 데이터 경보`, label `data-alert`. The body is a plain-Korean summary (what, since
  when, run link), the validation table, and `@jacksungjinlee` so Jack is notified regardless of who last edited a cron
  line. Comment on repeats.
- The job ends red.
- On recovery, comment `정상화됐어요` and close the issue.

**Dead-man's switch** — so a silent monitor can't hide a silent pipeline:
- Recommend [healthchecks.io](https://healthchecks.io) (free). Jack creates one check, period 1 day, grace 6 hours,
  email alert, and stores its ping URL as Actions secret `HC_PING_URL`.
- The watchdog pings it on every successful pass.
- If GitHub Actions stops running entirely, healthchecks.io emails Jack.
- Write Jack's exact steps in the PR.

**Keep-alive**
- Verify GitHub's 60-day inactivity rule for scheduled workflows.
- Re-enable both workflows monthly via the REST "enable a workflow" endpoint, not by committing (`main` will be
  protected).

Permissions: `contents: read`, `issues: write`, `actions: write` (enable endpoint only).

## Part 2 — Tests on every change (CI)

`.github/workflows/ci.yml` on `pull_request` (all) and `push` to `main`. The job is named `ci`.
- Pinned Node and Python, then `npm ci`.
- `bash build.sh`, then `git diff --exit-code baepsae.html` (the committed build matches `src/`). Remove this once
  Part 3 builds in the deploy.
- `pytest tests/`.
- `python tests/smoke_app.py` (Playwright Chromium installed in the job).
- `python tests/check_text.py`: 0 emoji, 0 banned words (from `docs/BAEPSAE_VOICE.md`), no bare `NaN` in JSON.
- Must finish in < 10 min.
- Prove it blocks: push a deliberately broken commit to a test PR, show the red check, then revert it.

## Part 3 — Protect `main` by splitting data from code

The data bot pushes to `main` daily, and the default Actions token can't be put on a ruleset bypass list. So
"pull request + green CI" can't be required on `main` without blocking the bot. Fix: data lives on a `data` branch, and
a deploy workflow publishes code + data together. Every step keeps the site working.

**3a — Add deploy, keep everything else unchanged**
- `deploy.yml`:
  - Triggers: manual only (for now).
  - Check out `main`, build from `src/`, and take the four JSON files from the `data` branch.
  - Run `validate_data.py --live` on exactly what will be published.
  - `actions/upload-pages-artifact` + `actions/deploy-pages`.
  - `concurrency: { group: pages, cancel-in-progress: false }`.
- `update-data.yml` now commits the validated JSON to **both** `main` (as before) **and** `data`.
- **Jack's clicks after merging 3a** (exact paths in the PR):
  1. Settings → Pages → Build and deployment → Source: **GitHub Actions**.
  2. Actions → Deploy → **Run workflow**.
  3. Open the site and check the 기준 date.
  4. The watchdog must be green.

**3b — Switch over** (only after 3a is live and green for one full day)
- Deploy triggers: push to `main` + success of 시세 데이터 갱신 + manual.
- `update-data.yml`: check out the `data` branch tip into the workspace **before** `fetch_data.py` runs. "Previous"
  data means that tip for every purpose:
  - validation comparisons;
  - the disclosure merge, which reads the old `disc.json` at fetch_data.py:837;
  - listing fallbacks.

  Missing previous = hard fail unless `bootstrap=true`.
- Stop committing JSON to `main`. Remove the four JSON files from `main` (history stays).
- Update `CLAUDE.md` rules 2–3, the repo map and `docs/HANDOFF.md`.
- Watchdog `workflow_run` now follows Deploy.

**3c — Lock `main`** (Jack's clicks, exact):
- Settings → Rules → Rulesets → **New ruleset → New branch ruleset**.
- Name `protect-main`; Enforcement status **Active**; Target branches → **Include default branch**.
- Rules:
  - **Require a pull request before merging** with Required approvals **0** (Jack can't approve his own PRs);
  - **Require status checks to pass** → add `ci`;
  - **Block force pushes**.
- Bypass list: **Repository admin**, set to **For pull requests only**, so a broken CI can't lock Jack out.
- The `ci` check only appears in the list after CI has run at least once. 3c comes after Part 2 for that reason.
